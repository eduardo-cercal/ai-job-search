# InfoJobs Search Skill

Search live job listings from InfoJobs (infojobs.com.br), a major Brazilian job board.
No authentication, no API key, and **zero runtime dependencies** — it runs with just `bun`.

> This is a market-specific skill generated by `/add-portal` for the Brazil job market
> (Portuguese-language postings). Per repo policy, market-specific portal skills like this
> one live in the user's fork rather than being merged upstream.

## Personal use note

`robots.txt` allows the `/empregos.aspx`, `/vaga-de-...aspx`, and `/mf-publicarea/...`
paths this skill uses (it disallows a set of unrelated account/legacy pages, plus
`/detailvacancy.aspx` and `/detailcompany.aspx` specifically — none of which this skill
touches). No Terms-of-Use restriction on automated access was located. As a precaution,
**treat this as personal use**: keep request volume low, don't use it commercially or for
bulk data collection.

## When to use this skill

- Search for job openings in Brazil by keyword, job title, or technology
- Narrow results to a specific Brazilian city or state
- Get the full description of a specific InfoJobs job listing
- Filter results by how recently they were posted (client-side — see Notes)

## Commands

### Search job listings

```bash
bun run .agents/skills/infojobs-search/cli/src/cli.ts search --query "<title>" [flags]
```

Key flags:
- `--query <text>` / `-q <text>` — **required.** Job title or keyword, e.g. `"desenvolvedor flutter"`.
- `--location <text>` / `-l <text>` — optional. A Brazilian city, e.g. `"Curitiba"`. Folded into the search keywords (InfoJobs has no separate location parameter for free-text place names — see Notes).
- `--jobage <days>` — only postings dated within N days. Client-side filter (InfoJobs has no server-side date parameter — see Notes). Omit for all postings.
- `--page <n>` — page number (1-indexed). Pages beyond 1 are fetched through InfoJobs' own infinite-scroll fragment endpoint.
- `--limit <n>` / `-n <n>` — cap total results emitted (client-side).
- `--format json|table|plain` — default `json`.

### Fetch full job detail

```bash
bun run .agents/skills/infojobs-search/cli/src/cli.ts detail <id|url> [--format json|plain]
```

`id` is the job ID from `search` results (e.g. `11828617`). You may also pass a full
InfoJobs `/vaga-de-.../<id>.aspx` URL — only the trailing numeric id matters, InfoJobs
resolves the posting from it regardless of the slug text. Returns the full description,
employment type, posted date, and valid-through date from the posting's own
`schema.org/JobPosting` structured data.

## Usage examples

```bash
# Flutter developer roles anywhere in Brazil
bun run .agents/skills/infojobs-search/cli/src/cli.ts search -q "desenvolvedor flutter" --format table

# Same, narrowed to a city
bun run .agents/skills/infojobs-search/cli/src/cli.ts search -q "desenvolvedor flutter" -l "Curitiba" --format table

# Mobile developer roles, posted in the last 7 days
bun run .agents/skills/infojobs-search/cli/src/cli.ts search -q "desenvolvedor mobile" --jobage 7 --format table

# Broader "desenvolvedor" search, page 2
bun run .agents/skills/infojobs-search/cli/src/cli.ts search -q "desenvolvedor" --page 2 --format json

# Full details for a specific job
bun run .agents/skills/infojobs-search/cli/src/cli.ts detail 11828617 --format plain
```

## Output formats

| Format | Best for |
|--------|----------|
| `json` | Default — programmatic use, passing IDs to `detail` |
| `table` | Quick human-readable scanning |
| `plain` | Reading a single job's full detail (`detail` command) |

All errors are written to **stderr** as `{ "error": "...", "code": "..." }` and the process exits with code `1`.

## Notes

- Page 1 is scraped from InfoJobs' public, server-rendered search-results HTML. Page 2+
  goes through InfoJobs' own infinite-scroll fragment endpoint
  (`/mf-publicarea/VacancyList/GetVacancyListFragment`), found by reading their shipped
  `list.js` bundle — see `url-reference.md`. Job detail is read from the posting's own
  `schema.org/JobPosting` JSON-LD block.
- **Location is folded into the search keywords, not a separate parameter.** InfoJobs'
  own location field resolves free-text city names to an internal id via an autocomplete
  API; appending a plain `&city=` query parameter has no effect (confirmed live). Including
  the city name in the query text does filter correctly, so `--location` does that for you.
- **No confirmed server-side date/recency parameter.** `--jobage` is implemented as a
  client-side filter over each result's own posted-date value, which is an exact
  `YYYY/MM/DD HH:MM:SS` timestamp (more precise than Catho's relative "Publicada Hoje"
  text). This means `--jobage` only filters *within whatever page you fetched* — it does
  not fetch additional pages to backfill a smaller-than-requested result set.
- InfoJobs may rate-limit; the CLI retries 429/5xx with exponential backoff. Keep volume
  low (see the personal-use note above).
- Job IDs are numeric (e.g. `11828617`) — pass them as-is to `detail`.
