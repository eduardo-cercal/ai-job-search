# We Work Remotely Search Skill

Search live job listings from We Work Remotely (weworkremotely.com), a large global
remote-jobs board. No authentication, no API key, and **zero runtime dependencies** — it
runs with just `bun`.

> This skill was generated by `/add-portal`. Unlike the Brazil-market portal skills in
> this repo, We Work Remotely is a global board — useful for the international
> remote-USD roles this candidate's Location Filter marks acceptable, alongside
> `arc-search`.

## Why this skill uses RSS, not HTML

Every ordinary page on this site (homepage, `/remote-jobs/search`, individual job pages)
returned an **HTTP 403 Cloudflare JS challenge** ("Just a moment...") for this CLI's
honest, non-browser User-Agent — confirmed live. Only the site's own `.rss` feed
endpoints returned real content (HTTP 200) with the exact same honest UA. This skill does
not work around the block by spoofing browser headers (that escalation path belongs to
`.claude/skills/job-application-assistant/09-web-research.md`'s robots.txt gate, not a
portal CLI's default) — it simply uses the feed, a legitimate first-class data source in
its own right, as its only data source.

Two consequences follow from this:
1. **No server-side keyword search.** The feed has none. `--query` is a client-side
   filter — see Notes.
2. **No separate detail-page fetch.** The feed already embeds each job's full
   description, so `detail` re-reads the same feed rather than fetching a second page.

## When to use this skill

- Search for remote developer/programmer/other jobs globally by keyword
- Filter by how recently a job was posted (using the feed's real publish date)
- Narrow by region (e.g. "Anywhere in the World" vs. "USA Only")
- Get a job's full description without an extra network round-trip

## Commands

### Search job listings

```bash
bun run .agents/skills/weworkremotely-search/cli/src/cli.ts search --query "<keyword>" [flags]
```

Key flags:
- `--query <text>` / `-q <text>` — **required.** Split into words and matched (AND, case-insensitive) against each listing's company, title, category, skills, and description text, e.g. `"flutter"` or `"react native"`.
- `--location <text>` / `-l <text>` — optional. Client-side substring filter over the feed's own `region` field, e.g. `"USA Only"` (most listings are `"Anywhere in the World"`).
- `--jobage <days>` — only postings within N days, using each item's real publish date.
- `--limit <n>` / `-n <n>` — cap total results emitted (client-side).
- `--format json|table|plain` — default `json`.

No `--page` flag — see Notes.

### Fetch full job detail

```bash
bun run .agents/skills/weworkremotely-search/cli/src/cli.ts detail <id|url> [--format json|plain]
```

`id` is the job slug from `search` results (e.g. `lemon-io-senior-react-native-developer-1`).
You may also pass a full `weworkremotely.com/remote-jobs/<slug>` URL. Re-reads the
combined feed and looks up the job by its own link — only finds a posting still present
in the feed's rolling window (see Notes).

## Usage examples

```bash
# Flutter-mentioning roles (matched via description, not just title)
bun run .agents/skills/weworkremotely-search/cli/src/cli.ts search -q "flutter" --format table

# React Native roles posted in the last 14 days
bun run .agents/skills/weworkremotely-search/cli/src/cli.ts search -q "react native" --jobage 14 --format table

# US-only engineering roles
bun run .agents/skills/weworkremotely-search/cli/src/cli.ts search -q "engineer" -l "USA Only" --format table

# Full detail for one job
bun run .agents/skills/weworkremotely-search/cli/src/cli.ts detail lemon-io-senior-react-native-developer-1 --format plain
```

## Output formats

| Format | Best for |
|--------|----------|
| `json` | Default — programmatic use, passing ids to `detail` |
| `table` | Quick human-readable scanning (the id column is never truncated — a cut id silently becomes a different, wrong id) |
| `plain` | Reading a single job's full detail (`detail` command), or a scan of search results with skills/category visible |

All errors are written to **stderr** as `{ "error": "...", "code": "..." }` and the process exits with code `1`.

## Notes

- **No server-side search parameter exists.** `q=`, `search=`, `query=`, and `keyword=`
  were not applicable (the feed has no query mechanism at all, unlike some HTML-scraped
  portals where these were probed and found to be no-ops) — `--query` is purely
  client-side, matched by word (AND) against company, title, category, skills, and
  description text. Description is included deliberately: a live check found a "Senior
  React Native Developer" posting whose title and skills field both omit "Flutter"
  entirely, but whose description mentions it as a nearby/alternative technology —
  without matching on description, a query for "flutter" would miss it.
- **No real pagination.** `?page=2` on the combined feed was probed live (fetched
  back-to-back with the unparammed URL to rule out the feed simply changing between
  requests) and confirmed byte-identical — a no-op. The feed always returns the latest
  ~10 postings from each of ~10 categories (~90 items total). Passing `--page` is
  rejected (`UNKNOWN_FLAG`) rather than silently accepted and ignored.
- Every result carries two bonus fields beyond the base contract: `skills` (WWR's own
  free-text skills list, e.g. `"Node.js, React, Mobile, React Native"`) and
  `employmentType` (e.g. `"Full-Time"`, `"Contract"`).
- `detail` only finds a job still present in the feed's rolling window. An older posting
  that has scrolled out returns `NOT_FOUND` — this does not mean the posting is gone from
  the live site, only that this skill's one data source (the feed) no longer carries it.
- We Work Remotely may rate-limit; the CLI retries 429/5xx with exponential backoff. Keep
  request volume low regardless.
